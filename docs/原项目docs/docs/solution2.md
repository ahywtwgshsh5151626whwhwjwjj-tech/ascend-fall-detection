# 方案二：工程结构化验证方案（Solution 2）

## 一、为什么需要方案二？

方案一已经完整验证了：
- 昇腾 NPU 推理链路的可行性
- 边缘侧实时视频处理与 UI 展示能力
- 真实业务场景下的端到端性能表现

但方案一的核心目标是 **​“能跑、能展示、能交付”​**，  
并不适合用来清晰解释系统的工程结构与演进逻辑。

因此引入方案二，用于回答一个不同的问题：

> **这个系统是否具备良好的工程结构、可扩展性和可维护性？​**

---

## 二、方案二的设计目标

方案二并不追求推理效果或性能指标，而是聚焦于：

- ✅ 明确模块边界（输入 / 推理 / 输出）
- ✅ 解耦业务流程与硬件实现
- ✅ 支持 mock → real 的渐进式演进
- ✅ 在缺失模型或硬件条件下仍可验证工程路径

---

## 三、方案一与方案二的关系

| 维度 | 方案一 | 方案二 |
|---|---|---|
| 核心目标 | 真实运行与展示 | 工程结构验证 |
| 是否依赖 NPU | 强依赖 | 可选 |
| 是否依赖模型 | 强依赖 | 可选 |
| 主要入口 | main.py / demo_tk_local.py | demo_solution2.py |
| 工程角色 | 交付路径 | 认知与解释路径 |

**方案二不会替代方案一，只是并行存在。​**

---

## 四、当前方案二实现说明

方案二的核心由三个部分组成：

- `core/solution2_engine.py`  
  负责抽象完整的业务流程（输入 → 推理 → 输出）

- `core/npu_engine.py`  
  方案一中的真实 NPU 推理实现，方案二通过接口方式复用其能力

- `demo/demo_solution2.py`  
  用于验证方案二工程路径是否完整可跑

当前阶段，方案二通过 `heartbeat()` 方式验证真实工程模块是否可被调用，
而不强制加载模型或执行推理。
